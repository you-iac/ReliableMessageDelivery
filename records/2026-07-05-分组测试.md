## 分组四：小规模业务压测

命令：

```bash
./bin/client 2 3 quiet 5
```

含义：

- 2 个发送方。
- 每个发送方发送 3 条消息。
- 本次期望发送总数 6 条。
- 最多等待 5 秒收集 ACK / push。

结果：通过，进程退出码为 `0`。

输出摘要：

```text
stress config: senders=2, messages_per_sender=3, total_messages=6, verbose=false, wait_timeout_seconds=5

Stress summary
  send_elapsed_seconds:  0.145
  ack_elapsed_seconds:   0.254
  push_elapsed_seconds:  0.145
  total_elapsed_seconds: 5.212
  send_ok:               6
  send_failed:           0
  receiver_login_resps:  1
  receiver_chat_pushes:  161
  sender_login_resps:    2
  sender_acks:           6
  client_write_throughput: 41.3793 msg/s
  server_ack_throughput:   23.622 msg/s
  receiver_push_throughput: 1110.34 msg/s
```

结论：

- 6 条消息全部发送成功。
- 发送方收到 6 个 ACK。
- 无发送失败。
- 接收方收到 161 条 push，大于本次发送量；原因是当前登录流程会补发 Redis 中已有 Pending 或最近消息，因此该值不能直接等同于本次新增消息数。

## 注意事项

- `./bin/client --help` 不会打印帮助，而是按默认参数启动压测；本次测试中曾误触发并随后中断。后续如果需要帮助参数，应先修改 client 支持 `--help`，避免误写入 Redis 测试数据。
- 当前 `client/main_client.cpp` 是压测客户端，默认参数为 `8` 个发送方、每个 `100` 条消息、等待 `30` 秒。
- 本次没有清理 Redis 历史数据，避免破坏已有测试现场。
- 测试期间没有停止或重启已有 `./bin/server` 进程。

## 总结

本次分组测试通过：构建、Redis 可用性、server 端口连通性、小规模业务发送和 ACK 链路均正常。需要进一步做严格端到端断言时，建议使用独立 Redis DB 或测试前后隔离 key，避免历史 Pending / recent 数据影响接收侧 push 计数。

- 因此当前测试口径下，server 在 `16` 个发送方、每个 `200` 条消息这一阶梯已经达到处理/ACK 收敛限制。

总体判断：本次达到的不是 server 进程崩溃限制，而是业务处理吞吐/ACK 收敛限制。稳定通过点为 `8 x 100 = 800` 条；失败点为 `16 x 200 = 3200` 条。后续若要找更精确阈值，可以继续在 `800` 到 `3200` 之间做二分压测，例如 `12 x 150 = 1800`、`14 x 180 = 2520`。
