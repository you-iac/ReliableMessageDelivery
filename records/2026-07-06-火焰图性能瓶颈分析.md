# 火焰图性能瓶颈分析

## 背景

本次分析基于一次服务端压测火焰图。压测场景中，客户端快速写入大量 `CHAT_REQ`，服务端通过 Muduo 接收、解码、入业务线程池，并在业务线程中完成消息创建、在线投递、状态更新和 ACK 处理。

需要区分两个概念：

- 消息数：客户端发送的业务消息数量。
- 任务数：服务端业务线程池中的事件任务数量。

一条聊天消息至少会产生两个业务任务：

```text
1. 发送方 CHAT_REQ 任务
2. 接收方 ACK 任务
```

因此在 160000 条消息压测中，业务线程池任务量至少约为 320000。若客户端超时重试、服务端重投或连接断开事件进入队列，实际任务数还会继续增加。

## 火焰图观察

### 业务线程瓶颈

火焰图中 `ServerEventDispatcher::handleChat` 占比约为：

```text
ServerEventDispatcher::handleChat    32.6%
```

其中主要消耗集中在消息存储状态写入：

```text
MessageStore::createMessage          15.2%
MessageStore::markDelivered          12.5%
MessageStore::markPending             2.3%
```

进一步展开后可以看到：

```text
EvalCreateMessage                    10.0%
EvalMsgStateScript                   10.5%
hiredis redisCommand                  9.8%
```

说明当前业务线程大量时间花在同步 Redis 命令和 Lua 脚本执行上。

当前一条在线聊天消息通常至少涉及：

```text
createMessage
markDelivered
markAcked
```

其中 `createMessage` 和 `markDelivered` 都发生在发送方 `CHAT_REQ` 处理路径中，接收方 `ACK` 还会触发 `markAcked`。

### IO 线程瓶颈

火焰图中 `ChatServer::onMessage` 占比约为：

```text
ChatServer::onMessage                35.8%
```

主要分为两部分：

```text
ServerEventDispatcher::enqueueEnvelope    19.2%
MessageCodec::DecodeAll                   13.5%
```

`enqueueEnvelope` 中的主要成本包括：

```text
ServerEvent::ServerEvent                   6.8%
std::function 构造                         3.2%
message::Envelope::operator=               3.1%
ShardedThreadPool::submit                  2.4%
ServerEvent::~ServerEvent                  2.2%
```

这说明 Muduo IO 线程并不只是收包，还承担了较多对象构造、protobuf 拷贝和任务包装成本。

`DecodeAll` 中的主要成本包括：

```text
std::vector::push_back                     6.6%
protobuf Parse / Merge                     4.7%
message::Envelope::~Envelope               1.5%
```

说明解码路径存在明显的临时对象和中转容器成本。

## 初步结论

第一瓶颈是 Redis 同步状态写入。

`createMessage`、`markDelivered`、`markAcked` 是可靠投递链路中必要的状态更新，但当前实现中每条消息会触发多次同步 Redis 操作。压测消息量增大后，这部分成为业务线程吞吐的主要限制。

第二瓶颈是 IO 线程中的解码和入队成本。

`onMessage` 中存在 protobuf 解析、`std::vector` 中转、`Envelope` 拷贝、`ServerEvent` 构造和 `std::function` 包装。这些成本会占用 Muduo IO 线程时间，使网络线程无法足够轻量地完成收包和转发。

第三个需要持续观察的问题是业务线程池分片不均。

状态面板中曾观察到部分 worker 队列长期明显高于其他 worker，甚至存在 worker 队列为 0 的情况。虽然一次消息会产生多个任务，队列总量超过消息数本身是正常的，但分片不均会导致热点 worker 拖慢整体完成时间。

## 优先优化方向

### 1. 降低 Redis 操作次数

优先考虑合并 `createMessage` 和 `markDelivered` 的 Redis 写入路径。

在线消息从创建到投递成功，当前至少要做：

```text
createMessage
markDelivered
```

可以评估是否通过一个 Lua 脚本完成：

```text
创建消息
幂等判断
若目标在线且已发送，直接设置 Delivered 状态
维护 Delivered 超时索引
```

这样可以减少一次 Redis RTT 和一次锁竞争。

### 2. Redis 连接池或分片连接

如果 `MessageStore` 当前使用单 Redis 连接并通过 mutex 保护，那么多个业务 worker 会在 Redis 访问处串行化。

后续可以考虑：

```text
1. 每个业务 worker 使用独立 Redis 连接
2. 引入 Redis 连接池
3. 按消息 key 或 uid 做 Redis 连接分片
4. 对批量状态更新使用 pipeline
```

### 3. 减少 IO 线程中的对象拷贝

`enqueueEnvelope` 中的 `Envelope::operator=` 和 `ServerEvent` 构造成本较明显。

可以考虑：

```text
1. DecodeAll 返回后，入队时 move Envelope
2. ServerEvent 构造函数接收右值 Envelope
3. enqueueEnvelope 增加右值重载
4. 避免在 IO 线程中做不必要的 protobuf 深拷贝
```

### 4. 减少 DecodeAll 中转成本

`DecodeAll` 当前会将解析出的 `Envelope` 放入 `std::vector`，之后 `onMessage` 再遍历并入队。

后续可评估：

```text
1. DecodeAll 预估数量并 reserve
2. 边解码边通过回调提交业务事件
3. 避免 `std::vector<Envelope>` 中转导致的 push_back 和析构成本
```

### 5. 补充状态指标

当前 `ThreadTaskNums` 只展示每个 worker 的当前队列长度。为了判断瓶颈，需要继续增加：

```text
1. 每个 worker 累计入队数
2. 每个 worker 累计出队数
3. CHAT_REQ / ACK / ConnectionClosed 分类计数
4. Redis create / markDelivered / markAcked 平均耗时
5. 客户端重试 duplicate 请求数量
```

其中入队/出队计数可以帮助判断是分片不均，还是某些 worker 执行耗时更长。

## 当前判断

这次火焰图表明，当前性能瓶颈不在客户端写入能力，而在服务端处理链路：

```text
Redis 同步状态写入成本高
IO 线程中解码和任务入队成本偏高
业务线程池可能存在分片不均
```

短期优先优化 Redis 写入路径，因为它直接占据 `handleChat` 的主要耗时。随后再优化 IO 线程中的 protobuf 拷贝和任务入队成本。
